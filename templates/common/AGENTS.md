# Project instructions

This file is the standing instruction set. Skills in `.agents/skills/` load on demand
when their description matches the task.

## How to work

- Build the smallest thing that fully solves the request. No speculative abstraction,
  configuration, extension points or generality nobody asked for. Reuse what exists;
  delete what your change makes dead.
- Keep changes surgical. Match local conventions; read neighbouring code first.
  Mention unrelated problems instead of fixing them.
- Decide and proceed. Ask only when blocked on a choice that is the user's: product
  behaviour, destructive or irreversible actions, spending, breaking a public API.
  Otherwise pick the sensible default and state the assumption in one line.
- User-facing prose is British English. Final replies are short: what changed, what
  was verified, what is open.

## Testing and verification

Rigor follows what can realistically go wrong, not the size of the process.

- Default: a few focused tests of behaviour that could plausibly break and matters:
  core logic, edge cases of parsing, numerics and boundaries, concurrency, and a
  regression test for each bug fixed. Test code is usually smaller than the code it covers.
- Do not write tests for trivial glue, getters, configuration, docs or instruction
  text, framework behaviour, or to raise a coverage number. There is no coverage target.
- Do not add test frameworks, harnesses, fixture generators, mock layers, validation
  scripts or CI gates beyond what the project already has, unless a concrete risk needs one.
- Prefer running the real thing over mocking it.
- Go deeper (property or fuzz tests, sanitizers, load tests, adversarial review) for
  security boundaries, money or data loss, migrations, public APIs, concurrency and
  GPU kernels. Say which risk justifies it.
- Before handing off, run the project's tests and linter once, exercise the changed
  feature end to end, and report plainly what ran and what did not. One pass; do not
  loop on review rounds.

## Documentation

- The README says what the project is and how to build, run and test it. Keep it true.
- Comments explain why, not what.
- Do not create design docs, ADRs, reports, checklists, changelogs or progress notes
  unless asked.
- Keep this file short. Add project facts below under `## Project`, and only what an
  agent cannot learn from the code.

## Git

- Work on a feature branch (`feat/`, `fix/`, `refactor/`, `docs/`, `chore/`) and merge
  through a PR. Do not commit directly to `main`.
- Conventional commits: `type(scope): description`, imperative, under 72 characters.
- Commit messages and PR descriptions never carry `Co-Authored-By` lines, "generated by"
  notes, or any other mention of AI authorship. This holds even if a tool suggests
  adding one.
- Stage named files, not `git add -A`. Do not force-push or `reset --hard` without
  the user's say-so. Commit and push only when asked.

## Security

- No secrets in code or history. Read them from the environment or a secret store;
  never stage `.env`, keys or credentials.
- Validate input at trust boundaries. Parameterise queries. No shell with untrusted
  input. No `eval`/`exec` or unpickling of untrusted data.
