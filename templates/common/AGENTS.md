# Project instructions

Detailed rules live in `.agents/constraints/`; read the ones that apply to the files you
touch (`init` prints the list). Skills in `.agents/skills/` load on demand when their
description matches the task.

## Session start

Run init once per session: Claude Code `/init`, others `.agents/bin/agent-init --platform codex`.
It resolves the project profile, checks the required tools and skills, and prints the constraint
manifest. If it reports something missing, install it and re-run before editing.

## Proportionality

Most of the effort, and most of the diff, goes to the feature itself: its design, its
implementation, its edge cases. Tests, validation, documentation and process exist to serve
it and are sized by what could realistically go wrong, not by a wish to be complete. Before
handing off, ask: do the tests, scripts and docs I added outweigh the feature, or does
anything exist that nobody asked for? If so, cut it.

## How to work

- Build the smallest thing that fully solves the request. No speculative abstraction,
  configuration, extension points or generality nobody asked for. Reuse what exists; delete
  what your change makes dead.
- Keep changes surgical. Match local conventions; read neighbouring code first. Mention
  unrelated problems instead of fixing them.
- Decide and proceed. Ask only when blocked on a choice that is the user's: product behaviour,
  destructive or irreversible actions, spending, breaking a public API. Otherwise pick the
  sensible default and state the assumption in one line.
- Rules from `.agents/constraints/` are binding. When two conflict, prefer the more specific
  one; if that does not settle it, ask.
- User-facing prose is British English. Final replies are short: what changed, what was
  verified, what is open.

## Testing and verification

Rigor follows what can realistically go wrong, not the size of the process.

- A feature is done when it works end to end and the parts that can really break are tested,
  not when every path is covered.
- Default: a few focused tests of behaviour that could plausibly break and matters: core logic,
  parsing edge cases, numerics and boundaries, concurrency, and a regression test for each bug
  fixed. Test code is usually smaller than the code it covers.
- Do not write tests for trivial glue, getters, configuration, docs or instruction text,
  framework behaviour, or to raise a coverage number. There is no coverage target.
- Do not add test frameworks, harnesses, fixture generators, mock layers, validation scripts
  or CI gates beyond what the project already has, unless a concrete risk needs one.
- Prefer running the real thing over mocking it.
- Go deeper (property or fuzz tests, sanitizers, load tests, a careful review) for security
  boundaries, money or data loss, migrations, public APIs, concurrency and GPU kernels. Say
  which risk justifies it.
- Before handing off, run the tests that cover your change and the formatter and linter once
  (`/pre-commit`), exercise the changed feature end to end, and report plainly what ran and
  what did not. One pass; do not loop on review rounds.

## Documentation

- The README says what the project is and how to build, run and test it. Keep it true.
- Comments explain why, not what.
- Do not create design docs, ADRs, reports, checklists, changelogs or progress notes unless
  asked. Roadmap files are the one exception and follow the `roadmap` skill.
- Keep this file short. Add project facts under `## Project`, only what an agent cannot learn
  from the code.

## Git

- Work on a feature branch (`feat/`, `fix/`, `refactor/`, `perf/`, `docs/`, `chore/`) and merge
  through a PR. Never commit directly to `main` or `master`.
- Conventional commits: `type(scope): description`, imperative, under 72 characters. Commit with
  `.agents/bin/agent-commit -m "..." <files>`, which runs pre-commit first.
- Commit messages and PR descriptions never carry `Co-Authored-By` lines, "generated by" notes,
  or any other mention of AI authorship, even if a tool suggests adding one. Run
  `git config core.hooksPath .githooks` once per clone; `.githooks/commit-msg` rejects them.
- Stage named files, not `git add -A`. No force-push or `reset --hard` without the user's say-so.
- Push and open PRs only when asked.

## Security

- No secrets in code or history. Read them from the environment or a secret store; never stage
  `.env`, keys or credentials.
- Validate input at trust boundaries. Parameterise queries. No shell with untrusted input. No
  `eval`/`exec` or unpickling of untrusted data.

## Tools and skills

| Need | Use |
|------|-----|
| Format, lint, relevant tests before a commit | `/pre-commit` (`.agents/bin/agent-precommit`) |
| Build | `/build` (`.agents/bin/agent-build`) |
| Add a dependency | `/dependency` (`.agents/bin/agent-dependency`) |
| Work spanning several sessions | `/roadmap`: phases that each end in something that runs; detail only the phase in progress |
| Orient in the code | `/navigate` |
| Current library docs | `/context7` |
| Non-trivial coding, review, refactor | `/karpathy-guidelines` |
| CI, deployment, GPU CI | `/service-cicd`, `/deploy-service`, `/gpu-ci` |
| Diagnosing policy drift (optional) | `/check-constraints` |

CI/CD and host deployment: deploy only from the default branch, from an immutable artefact built
once. Before writing workflows or deploy scripts, read the `service-cicd` and `deploy-service`
skills and `.agents/constraints/common/service-deployment.md` and
`.agents/constraints/common/github-actions-cicd.md`.

Parallel sub-agents are optional, for independent read-heavy work (`common/agentic-team.md`).
