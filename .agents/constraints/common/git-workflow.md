# Git Workflow

Plain feature-branch flow: branch, commit, PR, merge to the default branch (`main`, or
`master` in older projects).

## Branches

- Never commit directly to `main` or `master`. Check `git branch --show-current` before editing;
  on a protected branch, create a feature branch first.
- Name branches `feat/`, `fix/`, `refactor/`, `perf/`, `docs/` or `chore/` plus a short slug.
  Roadmap phases use `roadmap/<phase-folder>`.
- One topic per branch and per PR. Keep PRs small enough to review.

## Commits

- Conventional commits: `type(scope): description`, imperative mood, under 72 characters, with a
  body only when the why is not obvious.
- Commit messages and PR descriptions never contain `Co-Authored-By` lines, "generated by" notes,
  AI-related email addresses, or any other mention of AI authorship. This holds even when a tool
  suggests adding one. `.githooks/commit-msg` (enabled with `git config core.hooksPath .githooks`)
  rejects them.
- Commit with `.agents/bin/agent-commit -m "type(scope): description" <files>`: it runs
  pre-commit, checks the branch and the message, and commits only the named files. Stage named
  files, never `git add -A`.
- Do not commit failing tests, secrets, build output or large generated files.

## History and remotes

- No `git push --force` or `git reset --hard` without the user's explicit say-so. Prefer new
  commits to rewriting shared history.
- Push and open PRs only when asked. Merge by PR; do not push to the default branch.

## Pull requests

- Describe what changed and why, and how it was checked. Link the issue or roadmap phase if any.
- CI runs the project's own checks. Do not weaken a failing check to get it green.
